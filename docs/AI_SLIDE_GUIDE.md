# AI Agent向けスライド制作ガイド

Aizomeを使い、内容と余白の両方が整った発表資料を作るための判断基準です。設定の詳細は [README](../README.md)、Markdownの実例は [template.md](../template.md)、表示の実装は [aizome.css](../aizome.css) を参照してください。カタログの枚数・ページ番号をこの文書から推測せず、現在のファイルを確認します。

## 利用できる機械向け情報とツール

[レイアウト契約](../ai/layouts.json)から使用できるクラス、Markdown構造、項目数、併用条件を読みます。[ツールガイド](../tools/README.md)には静的・表示チェックと配布用ZIP作成の手順があります。[改善例](../examples/repairs.md)では指摘を受けて何から直すかを学べます。

作成後は利用可能な環境で `python3 tools/check_slides.py <資料.md> --json` を実行し、`findings` の問題を確認・修正します。静的に通ったあとも、実際の表示を確認します。ブラウザだけの場合は `tools/check-rendered.js` を実行して `await aizomeCheck()` を使えます。

HTMLを配布する場合は `tools/package_slides.py` で必要な素材をZIPにまとめ、作業フォルダとは別の場所に展開して再確認します。外部リソースが残る場合は、閲覧に接続が必要なことも成果物の説明に含めます。

## 1. 制作の進め方

1. **目的を読む。** 聴衆、伝えたい結論、持ち時間、希望枚数、利用できる資料、出力形式を会話から把握する。通常の判断は自分で進め、事実や目的に関わる不足だけを確認する。
2. **先に構成を作る。** 各スライドの「結論／根拠／見せ方」を短く整理する。調査報告なら結論→根拠→提案、手順説明なら全体→操作→注意点など、話す目的に合わせる。
3. **近い作例を選ぶ。** 下の選択表で共通レイアウトを選び、該当する実例のMarkdown構造を読む。クラス名だけを移植しない。
4. **内容を入れる。** 発表用の別ファイルに必要な作例だけを移す。作例の「指定：」「架空データ」やテンプレートの紹介文は、その説明自体が目的でない限り持ち込まない。
5. **密度を調整する。** 長文、行数のばらつき、図の縦横比を確認し、余白を確保する。出典・注釈の領域を先に見込む。
6. **参照を仕上げる。** スライド順を確定してから目次のページ番号、図表名、リンクを更新する。
7. **表示を確認して渡す。** 可能な環境で確認し、修正する。完成ファイル、確認結果、未解決の制約を簡潔に報告する。

短い資料に目次・章扉・プロフィール・締めをすべて入れる必要はありません。用途だけが違う同じ配置のスライドを、装飾目的で増やさないでください。

## 2. 内容からレイアウトを選ぶ

| 伝えたい内容 | 基本の指定 | 選び方 |
|---|---|---|
| 普通の説明 | クラスなし | 見出し、段落、短い箇条書きで足りる場合 |
| 結論・用語の定義・問い | `lead` | 大きな見出しと短い説明。質疑応答も同じ配置 |
| 項目・目次・要点 | `list` | 順番を示すなら番号付きリスト、不要なら箇条書き |
| 並列の説明・数値 | `cards` | 項目数で列数が決まる。2カラムも数値カードも共通 |
| 変更前後 | `cards before-after focus-right` | 2項目。同じ観点・順番・単位で比べる |
| 3案と推奨理由 | `cards focus-center` | 推奨するカードに「推奨」と理由も書く |
| 大きな数字1つ | `stat` | 数字を112pxに拡大。単位・対象・条件を添える |
| 複数案を同じ条件で比較 | `comparison-table` | カードでは比較軸が追いにくい場合 |
| 2軸による判断 | `matrix` | 行と列の意味が明確なマトリクス |
| 詳細項目・付録 | `dense` | 全幅の表。長文の逃げ場所にしない |
| 時間・工程 | `timeline` | `horizontal`・`split`・`numbered` を組み合わせる |
| スマホの操作手順 | `screen-flow` | 3〜4枚のスクショと、画面名・操作を順に並べる |
| 画像・図と説明 | `media` | リストで画像と本文を組にする |
| 画像同士の比較 | `gallery image-grid` | 2〜3画像。全体表示と切り抜きも比較可能 |
| 大きな画像1つ | `figure` | 図表名・説明を画像の下に置ける |
| 全体図と拡大 | `image-detail` | 元画像と切り出した画像の2枚を用意する |
| 背景全面の画像 | `full-image` | 意図して端まで使う場合。文字とのコントラストを確認 |
| 引用・利用者の声 | `quote` | 発言内容と発言者を分かるようにする |
| 人物紹介 | `profile` | 名前・役割・写真・詳細・SNSの専用構造を守る |
| 質問と回答 | `faq` | h2の質問と直後の回答段落を対にする |
| コード中心／解説付き | `code` / `cards code-notes` | 必要な範囲だけ抜粋する |
| 数式中心／導出 | `equation` / `align-middle` | 数式は標準の数式記法。導出を画像にしない |
| 判断・次の行動 | `decision` / `action` / `risk-action` | 理由・担当・期限・確認条件を目的に合わせて整理 |
| 出典の一覧 | `references` | 資料名と参照する内容をセットで書く |
| 表紙・章の切り替え・締め | `cover` / `section` / `closing` | 必要な場所だけに使う |

基本レイアウトは1つを選び、修飾クラスを足します。`cards media`、`timeline screen-flow` のように異なる配置を同時に指定しないでください。

### 覚える名前を増やさない

- `kpi`・`columns` は `cards`、`compare` は `cards focus-right`。
- `agenda`・`summary` は `list`、`definition` は `lead`、`qa` は `lead surface-tint`。
- `proof` は `align-middle`。数式自体はMarkdownの数式記法で書く。
- `recommend-first` / `recommend-middle` / `recommend-last` は `focus-left` / `focus-center` / `focus-right`。
- `four`・`grid` で項目数を指定しない。旧 `timeline-wrap`・`timeline-horizontal` も使わない。

CSSに過去の部品が残っていても、新規資料はREADMEに掲載された共通指定を優先します。用途名だけが違うクラスや作例を新設しないでください。

## 3. 密度と余白を設計する

次の数値は短い文章を想定した目安で、収まる保証ではありません。タイトル、注釈、コード、画像が加わると本文に使える面積は減ります。

| 内容 | 最初に置く量の目安 |
|---|---|
| 通常の本文 | 箇条書き3〜5項目。各項目は短くする |
| カード | 1〜6項目。見出し＋説明1〜2行。4個は2×2、5〜6個は3×2 |
| 時系列1列／横1段 | 6項目まで。横方向は特に短い見出しにする |
| 時系列2列／横2段 | 4〜10項目。奇数は前半が1件多くなる |
| スマホ画面 | 3〜4画面。長い操作説明を添えない |
| 比較表 | 3案×4項目程度。長いセルがあるなら項目を減らす |
| 詳細表 | 短い7項目程度。20pxの文字サイズを基準にする |
| 課題・対応表 | 3〜4件。課題、対応、確認時点をそろえる |
| 長いタイトル | `title-long` で2行まで。3行以上は本文に情報を移す |
| 出典／注釈 | 出典1行、注釈は短い2行まで |

はみ出したら、まず重複文を削り、項目の長さをそろえ、必要ならスライドを分けます。その次にレイアウトや余白を調整します。本文全体を小さくする、枠を画面端まで広げる、負の余白で押し込む、といった対処を最初に選ばないでください。

### 修飾クラスの選択

- **カード内の位置**：説明量が違うなら `card-top`。短い語句・数値中心なら `card-middle`。左右も中央にしたいときだけ `card-text-center`。
- **2枚の幅**：無指定で均等。主説明と補足なら `wide-left` / `wide-right`。3枚以上のカードには使わない。
- **強調位置**：`focus-left` は先頭、`focus-right` は末尾、`focus-center` は3枚の中央、`focus-both` は全カード。単一の推奨を示すなら強調を1箇所に絞る。
- **外側の余白**：標準は左右72px。必要なら `space-compact` / `space-standard` / `space-airy`。
- **間隔**：`gap-*` はパネル間、`inset-*` は対応するカード・画像枠の内側、`flow-*` は段落間。それぞれ `sm` / `md` / `lg`。
- **本文の位置**：`align-top` / `align-middle` / `align-bottom`。`content-left` / `content-center` / `content-right` は本文幅を64%に絞るため、専用の画像・時系列配置に重ねない。
- **タイトル**：`section-title` と `_header` で小さなセクション名。`title-long` で2行領域。`no-title` はタイトルと領域を取り除く。表紙・プロフィールなどの専用配置にタイトル用の修飾を安易に重ねない。
- **局所的な空間**：独立した段落として `![vspace-md](assets/spacer.svg)` を置く。通常の段落間隔に24pxが加わる。`xs` / `sm` / `md` / `lg` / `xl` / `2xl` は8 / 16 / 24 / 32 / 48 / 64px。

同じ軸の修飾は1つだけ選びます。クラスを並べる順番で優先順位が変わるわけではありません。空間を追加する前に、標準の余白で収まっているか確認してください。

### 色・文字

本文と見出しは同梱のM PLUS Rounded 1cです。別のフォントを追加する必要はありません。コード・数式の専用フォントは維持します。

配色は `palette-blue`・`palette-teal`・`palette-violet`・`palette-amber`・`palette-rose`・`palette-slate`。資料の基本色を決め、意味のある箇所にだけ別の強調色を使います。`surface-tint` は淡い背景、`surface-dark` は濃い背景、`emphasis` は太字の強調です。赤い全面背景や強い緑を独自に追加せず、既存パレットを優先してください。色だけで推奨・注意・完了を伝えないでください。

## 4. Markdown構造を守る

- 新規デッキの先頭にFront Matterを1回だけ置く。`marp: true`、`theme: aizome`、`paginate: true`、`size: 16:9` が基本。
- スライドの区切りは `---`。各スライドの指定は `<!-- _class: ... -->` を使い、次のスライドへの意図しない継承を避ける。`_header`・`_footer` もそのスライドだけに指定する。
- ディレクティブのHTMLコメントはMarpの設定として使用できる。本文用のHTMLタグとは区別する。
- カードはトップレベルのリスト項目が1枚に対応する。見出し・説明の間に空行を入れ、説明をインデントする。空項目を位置調整に使わない。
- `list`・`timeline`・`screen-flow` はトップレベルのリスト構造を守る。順序があるものは番号付きリストにする。
- `profile` は画像→名前h2→肩書き→紹介→3項目リスト→ひとことの引用→SNSの順。実例を読む。
- `faq` は質問h2→回答pの順。回答と次の質問の間隔を空行や空画像で補わない。
- h1は各スライドのタイトル。装飾のために本文中で追加しない。図表名にはh6を使う。
- Markdownに楽譜・Mermaid・PlantUMLのコードブロックを置いても、このテーマが自動で画像化するわけではない。

## 5. 画像・図・スクリーンショット

まず画像の実寸・縦横比・注目箇所を確認します。`ratio-1x1` / `ratio-16x9` / `ratio-4x3` / `ratio-3x4` / `ratio-9x16` / `ratio-3x1` から近い枠を選びます。例の灰色画像は配置確認用です。画像がない場合はプレースホルダーであることを明示し、実物の画像として扱わないでください。

- `media media-right` / `media media-left` は、Markdown上ではどちらも画像を最初のリスト項目、本文を2つ目に書く。
- `media-both` は左画像→本文→右画像。`media-wide` は両側画像とは併用しない。
- `fit-contain` が全体表示。`fit-cover` は切り抜き。顔・凡例・画面上の操作を切り落とさない。
- `media`・`image-grid` では `![crop 説明](...)` で中央、`![crop-top 説明](...)` で上端基準の切り抜きを選べる。
- 普通の画像は `![w:360](...)` などでサイズ指定可能。`media`・比率クラス・`image-grid` 内ではCSSがサイズを決めるため、寸法指定を重ねない。
- `diagram` は図の外周24px・本文との間48pxを確保する。楽譜やフロー図も通常の画像として配置する。ラベルが小さすぎるなら図を分割する。
- `image-detail` の拡大画像は自動生成されない。切り出した別画像が必要。`detail-left` で拡大を左へ置ける。
- 画像には内容の分かるaltを付ける。`crop` などの制御語と、画像の説明を併記する。

利用可能なSVGは `assets/generated/`、比率別の仮画像は `assets/placeholders/`、スマホ画面は `assets/screens/`、SNSは `assets/icons/` にあります。生成済み画像を表示するだけなら追加ツールは不要です。元の図や楽譜を編集して再生成する必要がある場合だけ、READMEの生成手順と環境を確認します。

絵文字コードはMarp標準の `:rocket:`・`:bulb:`・`:white_check_mark:` などが使えます。画像を外部配信元から取得するため、オフライン出力で欠けないか確認してください。未知のコードを推測で大量に使わないでください。

## 6. 出典・注釈・参照

数値・主張・引用の根拠は、提供された資料や確認できた情報に基づけます。不明な値やURLを捏造せず、確認待ちとして扱います。比較条件や単位もそろえます。

- `with-source` ＋ `<!-- _footer: 出典：資料名 -->`：短い出典1行。本文下部に112pxを確保。
- `with-notes`：スライドの最後の要素を引用ブロックにする。短い2行まで。本文下部に156pxを確保。
- 両者は併用せず、必要なら注釈欄に出典を含める。本文の `※1` と注釈番号は手動で対応させる。
- `captioned` ＋ `###### 表1：プラン比較`：表の直前に表名。図名は画像の直後。図表名はデッキ内で一意にする。
- `[表1](#表1プラン比較)`：上記の図表名への参照。この例では「：」を除いた文字列がリンク先になる。見出しの英字・空白・記号の変換は実際のHTMLのidで確認する。
- `[3枚目](#3)`：HTMLの3枚目へ移動。目次のページ範囲はカテゴリの先頭にリンクする。

TeXのような自動採番・自動参照更新はありません。順序変更後はページリンク、名前変更後は図表リンクを更新します。PDF・PowerPoint・エディタのプレビューでHTMLと同じリンク挙動を前提にしないでください。番号と名前だけでも意味が通じる文章にします。

## 7. 最小の制作例

次は、リポジトリ直下に別のMarkdownとして保存できる3枚の例です。実際の依頼ではタイトルと内容を目的に合わせて置き換えます。

````markdown
---
marp: true
theme: aizome
paginate: true
size: 16:9
---
<!-- _class: lead -->

# 改善の進め方

## 小さく試し、確認してから広げる

対象を絞って課題を見つけ、結果を次の判断につなげます。

---

<!-- _class: cards card-top -->

# 最初の検証で確認すること

- **分かる**

  説明なしで操作を始められるか。
- **進める**

  途中で迷わず完了できるか。
- **振り返る**

  改善すべき点を記録できるか。

---

<!-- _class: list -->

# 次の行動

1. **対象を決める**

   まず確認する操作を1つに絞ります。
2. **観察する**

   迷った場所と理由を記録します。
3. **改善を選ぶ**

   [確認する観点](#2)に沿って優先順位を決めます。
````

## 8. 保存・出力・確認

### ファイルと環境

- 指定がなければ新しいデッキはリポジトリ直下の `<資料名>.md` に保存すると、既存の `assets/...` パスを利用できる。下位フォルダに置く場合はMarkdownの画像パスと出力HTMLからのフォント・画像パスを確認する。
- `template.md` は作例カタログ。発表資料の依頼でカタログを置き換えない。テーマやカタログの修正が依頼された場合は、その対象を編集する。
- VS CodeとMarp拡張があれば編集・プレビュー・書き出しができる。制作のためにユーザーへNode.jsの導入を必須として要求しない。
- CLIが既に利用可能なら、その環境で書き出してよい。現在のCIの使用バージョンは [.github/workflows/pages.yml](../.github/workflows/pages.yml) で確認する。`npx` はパッケージをダウンロードする場合があるので、既存の実行環境を先に調べる。
- 出力HTMLを移動・共有するときは、フォント・画像の相対パスを保って `assets` も渡す。MarkdownとCSSは編集可能なソースとして残す。
- 現在のGitHub Pagesは `template.md` を公開する設定。新しいデッキを書いただけではそのデッキは公開されない。公開が依頼されていない限り公開設定を変更しない。

CLIが利用可能な環境での形：

```bash
marp presentation.md --theme-set aizome.css --output presentation.html
```

`marp` がなければ既存のVS Code拡張を使います。確認環境がなければ、静的確認を進めたうえで表示未確認と報告し、確認済みと装わないでください。

### 完了前の確認

1. **内容**：目的に沿った結論がある。重複する作例、テンプレートの操作説明、架空の人物・データが意図せず残っていない。
2. **Markdown**：Front Matter、スライド区切り、ローカルディレクティブ、リストのインデント、コードフェンスが正しい。廃止クラスを使用していない。
3. **表示**：タイトルと本文が重ならない。文字・表・図が切れない。本文と出典・注釈の間に余白がある。カードの内側の揃え方が意図どおり。
4. **画像・文字**：画像とフォントが読み込める。図のラベルが読める。切り抜きで必要な情報を失っていない。外部取得の絵文字も確認する。
5. **リンク**：目次は正しいページへ移動する。図表名が重複せず、参照が一致する。出典リンクも存在する。
6. **成果物**：Markdown、必要な追加画像、依頼された出力をそろえる。変更した内容と実施した確認を簡潔に伝える。

ブラウザで検証する場合は、実際の出力条件に合わせて画像を読み込み、各スライドを表示して確認します。要素がスライドの外に出ていないだけでなく、タイトル・本文・注釈間の重なりも確認してください。画像パスの検証用に追加した `<base>` はページ内リンクの移動先を変えるため、リンク確認では実際のHTMLの基準URLを使います。

## 9. テーマやカタログを改修する場合

新しい要求を既存のレイアウト＋修飾で表現できるか、先に確認します。共通化できるなら共通部品を使い、色・左右・項目数の違いだけで作例を追加しません。

新しい設定が必要な場合は、その目的と既存設定で足りない理由を明確にして、CSS・README・必要最小限の作例を一緒に更新します。クラスを廃止するときは移行先も説明します。スライドの増減・並べ替え時は、カタログの目次、READMEの一覧・枚数、ページリンクを更新し、代表的な組み合わせで表示を確認してください。

## 10. 制作中の改善をPRにつなげる

作者は、利用中に生まれた再利用可能な改善のPRを歓迎しています。テーマの不具合修正・共通配置・制作ガイドなどを改善したら、本来の成果物を完成させたあと、[貢献ガイド](../CONTRIBUTING.md)を読んで還元できる変更を整理します。

発表の本文や組織専用の設定だけならPRを勧める必要はありません。共通の改善なら、実際の効果を添えて一度案内します。

> 今回の「〇〇の修正」はほかの資料にも役立ちます。作者は改善PRを歓迎しています。発表内容を含めず、共通部分だけをPRしてみませんか？

案内の前に、汎用サンプルへの置き換え、差分の切り分け、可能な検証、PRタイトルと本文の準備まで進めます。ユーザーがその変更のPR作成を依頼している、または改善の継続的なPR提出を許可している場合は、重ねて確認せず、認証・提出先・既存PRを確認して作成します。

提出先、forkからの手順、CLIがない場合の代替、作成後の報告は [CONTRIBUTING.md](../CONTRIBUTING.md)、本文の構成は [PRテンプレート](../.github/pull_request_template.md) を使います。作者がPRを歓迎していても、利用者の非公開資料まで公開してよいことにはなりません。
